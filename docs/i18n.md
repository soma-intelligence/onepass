# Localization

OnePass ships in **French** (source), **English**, **Spanish** and **Italian** on every surface a
person reads: the Apple apps (iPhone, iPad, Mac, Watch, Vision), their extensions (AutoFill, widgets,
notifications, App Shortcuts, permission prompts) and the browser extension. A language the device
asks for that OnePass does not have falls back to English. The CLI and the MCP server stay in English
(terminal and agent tools, output read by scripts).

Design and rulings: [`docs/superpowers/specs/2026-11-02-i18n-four-languages-design.md`](superpowers/specs/2026-11-02-i18n-four-languages-design.md).

## The rules, in short

1. **Every new string gets a semantic key and all four languages** in the same commit.
2. **Keys are stable**: `area.screen.element`, lowerCamelCase segments joined by dots
   (`settings.general.autoLock`, `items.empty.title`, `travel.banner.body`). The key never changes
   when the text changes; the French text is the `fr` value of the entry.
3. **Product terms and shared actions come from the glossary** (`scripts/i18n/glossary.json`):
   `term.vault`, `term.passkey`, `term.watchtower`, `term.travelMode`, `common.cancel`,
   `common.done`... Use those keys instead of a new one. Their catalog values are copied from the
   glossary by `i18n.py sync`; never edit them in a catalog.
4. **No sentence assembled from pieces.** See [Composition](#composition).
5. **Plurals are plural variations**, never `n > 1 ? a : b` or "élément(s)".
6. `python3 -I scripts/i18n/i18n.py check` must pass (CI runs it: `.github/workflows/i18n.yml`;
   locally `make -C apple i18n-check`).

House tone: French uses **tu**, so Spanish uses **tú** and Italian **tu**. Short, plain, Apple-like
(the system's own words: Ajustes, Impostazioni, llave de acceso, Riempimento automatico). English
titles and buttons use Title Case as today; Spanish and Italian use sentence case.

## Swift (String Catalogs)

Each target has a `Localizable.xcstrings` (source language `fr`). Add the entry by hand in Xcode's
catalog editor (or in the JSON) with the key, the four values and a comment that says where the text
appears. The project sets `STRING_CATALOG_GENERATE_SYMBOLS`, so Xcode generates a symbol per key:

```swift
Text(.settingsGeneralAutoLock)                       // key settings.general.autoLock
String(localized: .itemsAddTo(vault.name))           // key "items.addTo %@", fr "Ajouter à %@"
Button("common.cancel", role: .cancel) { dismiss() } // APIs that take a LocalizedStringKey
```

- A key with arguments keeps its format specifiers at the end, in order: `items.addTo %@`,
  `watchtower.scan.progress %lld %lld`. Each language may reorder them with positional specifiers
  (`%2$@ … %1$lld`).
- Swift packages (VaultKit, DesignKit) look strings up in their own bundle: the generated symbols do
  that for you; a literal needs `bundle: .module` (VaultKit: `VaultKitStrings.bundle`).
- Plurals: in the catalog editor, *Vary by Plural* on the entry, `one` and `other` in every language
  (French `one` covers 0 and 1).
- A string that must not be translated (a brand, a code): `Text(verbatim:)`, or mark the entry
  *Don't Translate*.
- `CoreLabels.xcstrings` (labels of the item templates of the Rust core) is generated: edit
  `apple/scripts/core_labels/{en,es,it}_core.py` and rerun `gen.py`.
- `InfoPlist.xcstrings` (permission prompts) and `AppShortcuts.xcstrings` (Siri phrases, which must
  keep `${applicationName}`) follow the same rules.

**Legacy keys.** Most existing entries are still keyed by their French text (`Text("Réglages")`).
They keep working. When you touch one, or a whole screen, migrate it:

```sh
python3 -I scripts/i18n/i18n.py rekey apple/App/Resources/Localizable.xcstrings --only settings --dry-run
python3 -I scripts/i18n/i18n.py rekey apple/App/Resources/Localizable.xcstrings --only settings
```

`rekey` renames the entries of one area (the first folder under the target, like `Settings`) and the
matching Swift literals, keeps every translation, and maps exact glossary matches to `term.*` /
`common.*`. Build afterwards: a literal that was not a localized lookup would now show its key.

## Browser extension

Strings live in `extension/src/shared/l10n/{fr,en,es,it}.json`, one flat object per language:

```json
{
  "menu.noLogin": "Aucun login pour {site}",
  "menu.otherAccounts": { "one": "Autre compte {name}", "other": "Autres comptes {name}" }
}
```

```ts
import { t, tn } from "../shared/i18n";
t("menu.noLogin", { site: hostOf(origin) });
tn("menu.otherAccounts", count, { name });
```

`Key` is the type of `fr.json`'s keys: a language file without a key, or a call with an unknown key,
fails `npm run typecheck`. Arguments are named (`{site}`), never positional. The language is the
browser's UI language when it is French, Spanish or Italian, English otherwise. The three manifest
strings live in `extension/src/_locales/<lang>/messages.json`. `tr(fr, en)` is gone and the check
refuses it.

## Composition

Composing text from smaller pieces is allowed only where the grammar of **every** language holds:

- **Allowed:** an argument that is data or a proper noun (`%@` = a site, a vault's name, a number, a
  date already formatted by a `FormatStyle`); a list joined by `ListFormatter` /
  `Intl.ListFormat`; a whole sentence per case (`switch` over the cases, one key each); a glossary
  term **as a whole label** (a tab title, a section header, a button).
- **Not allowed:** concatenating fragments (`"Supprimer " + name`, `t("a") + " " + t("b")`);
  inserting a glossary term inside a sentence (`"Delete %@"` with `%@` = "vault": articles and
  gender agree differently in French, Spanish and Italian: *le coffre*, *la bóveda*, *la
  cassaforte*); choosing singular or plural in code; building a word from a prefix or suffix.
- Inside a sentence, write the glossary term's form directly. `i18n.py check --terms` warns when an
  English sentence uses a term and a translation does not use the glossary's word for it.

## The checker

`python3 -I scripts/i18n/i18n.py check` fails when:

- an entry misses one of the four languages, is empty, or is still in the `new` state;
- placeholders differ between French and another language (`%@`, `%lld`, `%1$@`,
  `${applicationName}`, `{site}`, `$1`); a plural `one` may omit the number;
- a plural lacks `one` or `other`;
- a `term.*` / `common.*` entry differs from the glossary;
- an extension language file has more or fewer keys than `fr.json`;
- any text contains an em dash;
- the extension still calls `tr(`.

`stats` prints coverage per catalog, and the count of legacy keys still to migrate.

## Adding a language

1. Add its code to `languages` in `scripts/i18n/config.json`.
2. `python3 -I scripts/i18n/i18n.py export de --out de.json`: one entry per string, with the French,
   the English and the comment, and an empty `de` value (a `one`/`other` object for plurals). This
   includes the extension's strings.
3. Translate `de.json` (a translator, or a model given this page and the glossary). Add a `de`
   column to every entry of `scripts/i18n/glossary.json`.
4. `python3 -I scripts/i18n/i18n.py import de.json --lang de`, then `i18n.py sync`.
5. `apple/scripts/core_labels/de_core.py` (copy `it_core.py`), add it to `gen.py`, rerun it.
6. Add `de` to `knownRegions` in `apple/project.yml` (and regenerate the project), and
   `extension/src/_locales/de/messages.json`; add `de` to `Lang` in `extension/src/shared/i18n.ts`.
7. `python3 -I scripts/i18n/i18n.py check` until it passes.

No Swift or TypeScript code changes beyond step 6.
